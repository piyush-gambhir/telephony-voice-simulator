# Extending the simulator

The Python backend owns execution, validation, persistence, and grading. The
console consumes the control API; its scenario reference is generated by
`pnpm content`. Add behavior at the existing boundary instead of introducing
another database or provider-specific scenario format.

## Add an AMD scenario

Add a uniquely named YAML file to
`apps/simulator-backend/src/telephony_voice_simulator/scenarios/`. For installed
packages or private scenario packs, set `SIMULATOR_SCENARIOS_DIR` to an external
directory. This replaces the bundled AMD directory; built-in IVR/PBX scenarios
remain available. Use the same environment for the API and `pnpm content`, then
restart the API and rebuild the static console.

This example requires no speech asset:

```yaml
name: short_voicemail
machine:
  max_duration: 40
  main:
    - wait: 0.5
    - tone: {freq: 1000, duration: 0.4}
    - hold: 30
expect:
  callee_class: machine
  agent_spoke: true
  message_start_after: {mark: tone_end, min: 0, max: 3}
```

Run `pnpm scenarios:check` or, from the backend directory:

```bash
uv run telephony-voice-sim validate --scenario /absolute/path/short_voicemail.yaml
uv run telephony-voice-sim validate --all --scenarios-dir /absolute/path/private-scenarios
```

Validation never places calls or creates a database. It checks names, step and
expectation vocabulary, types, finite durations, timing windows, DTMF keys,
branch targets, and duplicate names. It does not guarantee that referenced
speech assets exist or have release approval. Follow [the asset policy](ASSET_POLICY.md)
for audio provenance and serving permissions.

`scenario_validation.py` is the shared schema used by the catalog, runners,
PSTN compiler, benchmark loader, and content generator. Add any new step or
expectation there and implement its behavior in each applicable transport.
Each step has exactly one operation. Asset paths stay inside the corpus;
`repeat_from` references an earlier step; DTMF branches reference a named
sequence. `dial` is a PSTN operation. `max_duration` bounds room execution;
PSTN uses recording limits and bounded gather retries.

Grading has three outcomes: true, false, and indeterminate (`null`). Any
failed check fails the grade; otherwise an unavailable required check keeps
the grade indeterminate. `callee_class` labels benchmark ground truth and is
not an assertion. Room mode reports `message_content` as indeterminate because
isolated mailbox transcription is implemented in PSTN grading. Empty grades
never count as a pass. Test temporal behavior with synthetic audio rather than
calling a carrier or transcriber in the test suite.

## Add a provider

Implement `ProviderAdapter` in `telephony/providers/`. Its descriptor declares
endpoint kinds and supported scenario kinds; the console uses the API's
scenario compatibility results rather than maintaining its own carrier list.
Implement profile/endpoint validation, runtime readiness, and asynchronous
dispatch. Provider execution should return a normalized `RunDispatch` and
use the `ProviderRuntimeStore` port for durable queue ownership.

Register the adapter in `telephony/registry.py`, or inject a provider mapping
into `SimulatorService(providers={...})` for an integration or test. Mapping
keys must match descriptor keys. A profile is validated before it is saved.
Do not present a preview adapter as ready for live calls. Number provisioning
currently uses the dedicated Twilio management client; another carrier needs
an explicit management integration as well as a call adapter.

Queued-run cancellation removes only unclaimed queue work. The database
arbitrates cancellation against an incoming call claiming that run. Cancellation
returns a conflict once work is claimed; it does not hang up an active call.
Use `GET /api/runs/{id}` and `POST /api/runs/{id}/cancel`, or
`telephony-voice-sim cancel-run <id>`.

## Add IVR or PBX behavior

Built-in IVR/PBX definitions live under `domains/` and share
`ScenarioDefinition` and `TimelineStep`. Keep simulated timelines consistent
with their terminal outcome and elapsed duration. Add a case asserting the
observable routing decision, terminal event, and relevant timing.

The richer dealer-group model lives under `pbxsim/`. Start with
[`DEALER_GROUP_PBX.md`](DEALER_GROUP_PBX.md); validate new groups with
`validate_group` and test routes, schedules, capacity, and transfer outcomes.
This is a deterministic model, not a SIP registrar.

## Extend the console

`use-console-data.ts` owns resource fetching, partial failures, refresh,
request cancellation, and protection against stale snapshots overwriting mutations.
Use `updateData` after successful mutations. History filtering, export, and
paging live in dedicated run/call components; reusable display helpers live in
`console-status.tsx`. Keep endpoint compatibility in
`lib/scenario-compatibility.ts`, driven by backend catalog data.

Run `pnpm lint`, `pnpm test`, `pnpm scenarios:check`, and `pnpm build` before
shipping. For asset, packaging, or deployment changes also run the existing
prompt, UAT, license, and public-release checks. Keep tests that protect
observable behavior; avoid source-code string checks, arbitrary catalog-count
thresholds, and assertions about private class/module names.
